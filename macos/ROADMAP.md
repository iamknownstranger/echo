# Echo Music for Mac · product and provider roadmap

**20 November 2026.** Start with a room a Mac and an Android phone can already understand. Then let listeners bring their collections from other services. A listener should be able to paste an album link, see which tracks Echo can use in their market, and know exactly which recording will play before inviting a friend.

## Starting point

The Mac client already searches and plays YouTube Music, opens Echo song links, imports local audio, saves likes and playlists, downloads available streams, and displays timed lyrics. Its saved track source is either a YouTube video ID or a file URL. Android already has Media3, account and Spotify library features, multiple lyrics sources, playback extensions, offline media, and Listen Together. The first delivery below adds the Mac room client. The remaining milestones are proposed work. [Mac guide](README.md) · [Mac track model](Sources/EchoMusic/Models.swift) · [Android feature inventory](../README.md)

Antra's seven headline services cover several different jobs. Its dispatcher also accepts SoundCloud, its audio chain includes JioSaavn and optional Soulseek, and its tree contains a NetEase adapter outside the active chain. TIDAL's HiFi and mirror routes are implementations of a service. Song.link, MusicBrainz and lyrics services supply information about recordings. Counting each of these as a playable subscription would give users the wrong expectation. The inventory below uses the Antra revision in this workspace. [Antra feature guide](https://github.com/anandprtp/Antra/blob/e03154a40281831814189a85d859e6a8f98b84af/FEATURES.md) · [Source registration and link dispatch](https://github.com/anandprtp/Antra/blob/e03154a40281831814189a85d859e6a8f98b84af/antra/core/service.py) · [NetEase implementation](https://github.com/anandprtp/Antra/blob/e03154a40281831814189a85d859e6a8f98b84af/antra/sources/netease.py)

Record platform, market, access tier and last successful check. Enable an action after it succeeds for that combination. ## Order of delivery and release gates

The order follows technical dependencies. Provider approvals can proceed in parallel from the second milestone. Release individual capabilities as they pass their gates, so a closed beta cannot block improvements to local libraries.

| Milestone | Deliverable and work owner | Exit criteria |
| --- | --- | --- |
| 0 · Listen Together | Mac player and room client. Host or join the existing Android room, approve a guest, share its code, synchronize the current recording, queue, playback state and position. Resolve each track on each device. | Test Mac hosting Android and Android hosting Mac. Exercise late join, pause, seek to zero, track changes, ordered repeated tracks, local-only items, disconnect and leave. Measure audio skew separately from message transit. |
| 1 · Recording identity and imports | Shared contracts, catalog and library owners. Introduce provider IDs, original URLs, market, recording/release IDs, duration, version, explicitness and capability state. Keep playlist occurrences separate from recording identity. Add the link parser, import preview and a per-row result. | Migrate an existing Mac library and Android database fixture with likes, playlists, repeats, files and downloads intact. Import a paged 1,000-row playlist with a failed middle page, retry it, and verify order and counts. Unsupported links open their source and retain the original URL. |
| 2 · Personal catalogs | Provider adapters and both client UIs. Ship Apple Music and eligible Spotify import first. Add SoundCloud and the remaining named services in the matrix as access permits. Browse songs, albums, singles, EPs, artists, discographies, playlists, followed artists and saved items according to source capability. Include show and episode links where supported. | For each adapter, test expired authorization, missing scope, unavailable release, partial album, empty account, quota backoff and cancellation. Display fetched, skipped, ambiguous and unavailable counts. A user can disconnect an account and remove imported account data. |
| 3 · Source selection and playback | Player and metadata owners. Offer source selection, recording-match review, explicit/clean preference, artwork and timed lyrics. Show which source, edition and quality is playing. Integrate provider-native players where credentials and product terms permit. | Test strict matches against live/studio, remaster, remix, cover, explicit/clean, translated title and equal-title/different-artist pairs. An ambiguous match requires a listener choice. Transport, keyboard controls and system Now Playing work on every enabled player. |
| 4 · Offline and organized library | Desktop library and Android offline owners. Queue authorized downloads and user-owned file operations. Support per-track progress, bounded concurrency, pause/cancel, resume, individual/batch retry, storage limits and history. Add tag editing and export profiles for FLAC, ALAC, AAC and MP3 where supported. | Recover from interruption, disk-full, moved originals and a truncated transfer. Verify decoded duration, stream properties and actual playable media before atomic replacement. Keep managed subscription caches separate from exportable files. Exercise multi-disc albums, disc numbering, filename collisions, sidecars and deduplication. |
| 5 · Mixed-provider rooms | Android, Mac and relay owners together. Negotiate a versioned recording identity extension and device playback capabilities. Choose a compatible edition and let each participant resolve it in their account and region. Add room chat, track suggestions/voting, richer moderation and invitation QR parity where missing. | Run old Android with new Mac, new Android with old Mac, and both new. If either side lacks the extension, send only compatible legacy IDs. Show unavailable participants an explanation and rejoin action. A different cut, blocked market or subscription expiry must never silently play a different song. |
| 6 · Library maintenance and Mac parity | Library, desktop UX and release owners. Add scheduled opt-in playlist refresh, changes since last sync, album availability by market, provider health and user-readable failure history. Improve offline search, discovery, listening history, optional recommendations and podcast resume. Assess EQ, gapless/crossfade, output routing, lyric offsets and additional themes against Android use cases. | Re-run refresh after sleep, clock/time-zone change and revoked access without duplicating tracks. Respect user removal and source order. Test VoiceOver, keyboard-only use, system appearance, slow network and 10,000-track navigation. Package and verify on supported Mac hardware before broader rollout. |

### Decisions that affect several milestones

- **Recording matching.** Prefer a confirmed provider ID, then a verified ISRC plus duration and edition. Use title, artist credits, version markers and duration to propose candidates when IDs are missing. An ISRC shared by multiple releases cannot identify album art, track order or the intended mastering by itself. Preserve the user's override, its market and its source. Add negative fixtures as new collision patterns appear.
- **Library operations.** Let users choose recording-level deduplication or complete-album preservation. Preview artist/album/disc folder templates and conflicts before changing files. Tag title, artists, album artist, disc/track, year, composer, genre, ISRC, artwork and licensed lyrics. Offer loudness, bit depth and sample-rate inspection for owned files. Label transcodes by their actual source and output. A frequency cutoff on its own cannot establish provenance.
- **Room timing.** Existing Android room tracks identify a video by its bare ID. Media3 and AVPlayer resolve audio independently. Relays exchange track metadata, millisecond positions, play/pause state and readiness. On a route change, obtain fresh clock samples. Cover stale events, buffering before and after a seek, repeated songs, host handoff and a relay restart. An offset between two players’ reported positions and a difference between speaker outputs are separate measurements. [Android protocol](../app/src/main/kotlin/com/music/echo/listentogether/Protocol.kt) · [Timing model and network test](../app/src/test/kotlin/com/music/echo/listentogether/ListenTogetherWlanTest.kt) · [Metroserver](https://github.com/MetrolistGroup/metroserver)
- **Credentials and failure reporting.** Use scoped sign-in, Keychain/Keystore for credentials and per-provider revocation. Respect rate limits and retry delays. Record anonymized operation, elapsed time and failure category locally. A server URL and a pasted invite are different inputs. Keep session tokens, private playlists, signed audio URLs, local paths and provider credentials out of invites and diagnostics.
- **Quality measurement.** Before promoting each adapter, report exact/ambiguous/unmatched counts on a versioned catalog fixture, first-page latency and import completion after retry. For rooms, report median, p95 and worst observed playhead skew on a quiet LAN and a jittered connection, plus recovery time after a stall. For an acoustic claim, record both physical outputs against a common reference and include output route, sample count and hardware. Publish the measured capabilities and limitations per platform.

The first provider milestone is complete when someone can import their own playlist, inspect uncertain matches, restart Echo and find the same ordered selections. Mixed-provider room playback follows only when both clients and the relay can identify the same playable edition.
